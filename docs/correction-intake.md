# Sharing real correction examples

One example is enough to start reviewing whether the lesson format fits a real correction. A broader evaluation needs roughly 10–20 distinct, reviewed examples and repeatable tasks. There is no need to recover old chats if none are available; future corrections can be recorded as they happen.

## Minimum for one example

Copy this short form and fill it in using your own words:

```text
Original coding task:
What the agent did that you corrected:
Your correction and the behavior you wanted:
When this should apply again:
When it should not apply:
May we use this scrubbed example for local product testing? yes/no
```

For a meaningful coding outcome study, also provide the language/framework and relevant dependency versions, a reproducible starting commit or a small shareable fixture, the check that showed success or failure, and the actual outcome. Those details may be omitted for an initial lesson review; an unverified outcome will be labeled as such. A report that a test ran is a developer attestation unless the tool itself observes the run.

Remove names, client information, repository URLs, source code, secrets, logs, account identifiers, and proprietary details before sharing. A generic summary is preferable to a transcript. You control whether an example is used only in local evaluation or may appear in public anonymized fixtures; publication requires separate explicit permission. We will show the proposed lesson and scope for review before treating it as approved.

If there are no real examples yet, development can continue with synthetic fixtures, host compatibility, and safety testing. Those results cannot establish a reduction in real developer corrections.
